1. 只使用 FlashDuty 告警详情中的 `alarm_host` 和 `alarm_port` 作为告警端点，调查窗口固定为告警发生前五分钟至告警发生时。字段缺失时如实说明。
2. 按 MCP 动态发现的工具描述和 Schema 自主选择调用，每次调用后根据真实返回决定下一步。若发现认证工具，根据当前会话状态自主判断是否调用；Host 不会预先调用或隐藏固定认证工具。实例 ID、数据库、表和字段必须来自工具返回，不猜测部署结构。
3. 先用MCP发现allowlist中的archery实例及archery数据库；记下其真实MCP instance_id。在后续元数据与查询调用中必须使用该实例 `instance_id` 和数据库 `db_name = archery`。
4. 查询 `t_instance_member` 的真实字段，查询条件使用告警详情的 `alarm_host`、`alarm_port` 等值于`f_ip`、`f_port`，取得 `f_instance_id`；再查询 `sql_instance`，在SQL的WHERE条件中以`f_instance_id`的值等值于`id`查询真实host和port。
5. 将`sql_instance`返回的真实host和port严格组合为host:port，作为`mysql_slow_query_review_history.hostname_max`的等值条件；确认 `mysql_slow_query_review_history` 的`hostname_max`真实字段和时间字段，再在实例`archery`和`db_name=archery`中用`hostname_max`等值条件和告警时间范围条件共同查询慢查询日志记录，时间范围条件必须包含`ts_min`下界（完整条件见第7条），排序条件用`order by id desc`；两类WHERE条件缺一不可。最终结果应包含 `hostname_max` 以及时间、数据库、用户、checksum、sample、执行次数、耗时等实际存在且有分析价值的字段。
6. 若Archery MCP返回结果因内容过长被MCP截断，则先进行一次`SELECT id FROM ……`查询语句（WHERE条件中仍需包含带`ts_min`下界的告警时间范围条件和`hostname_max`等值条件，见第7条），然后再根据返回的id值添加到查询`mysql_slow_query_review_history`的SQL语句的WHERE查询条件中，分别查询每个id对应的`mysql_slow_query_review_history`日志，最后再合并起来，将合并结果作为`mysql_slow_query_review_history`的最终查询结果，结束Archery调查。
7. 若表中存在 `ts_min`、`ts_max`，它们分别表示聚合记录首次与末次发生时间，可用 `ts_min < '<end_beijing>' AND ts_max >= '<start_beijing>'` 判断窗口重叠，且必须为 `ts_min` 补充下界，完整时间条件为 `ts_min >= '<ts_min_lower_bound_beijing>' AND ts_min < '<end_beijing>' AND ts_max >= '<start_beijing>'`（慢日志按5分钟归并入库，1小时余量足以覆盖跨窗口的聚合记录，不会漏配）。禁止提交只有 `ts_min < 窗口结束` 的开放范围：该写法会使优化器选择主键倒序扫描，一旦窗口内匹配行数凑不满 LIMIT 便退化为全表倒序扫描而超时被kill。其它字段应依据其真实名称和类型构造时间条件，不得改变告警窗口，注意时区为北京时间。
8. 若窗口查询超时或报错，依据真实错误、字段和索引信息调整下一次查询；不要原样重复无效调用。没有匹配记录或链路无法完成时，如实返回空结果或错误，不得把告警标题中的端点替代 `hostname_max`，也不得虚构日志。
9. 成功取得 `mysql_slow_query_review_history` 结果后结束 Archery 调查。登录、实例成员解析、表结构和索引等辅助响应只作为内部审计 artifact 保存；只有最终 history 查询结果经过程序侧过滤、聚合和排序后进入主 Agent 上下文。
